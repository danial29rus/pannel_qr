# Развёртывание панели рядом с Витриной и подключение партнёра

Инструкция описывает текущие deployment-конфиги в `vitrina-ai` и `pannel_qr`. DNS для `panel.<домен-витрины>` уже должен указывать на IP сервера. В QR-панели уже реализованы выбор случайного активного пользователя с email из загруженного пула, входящий merchant API и лимиты проекта. Но нужный вам маршрут, где панель сама вызывает API Витрины за платёжной ссылкой, пока не реализован. Поэтому вначале можно развернуть панель и проверить входящий поток с провайдером, который возвращает прямой НСПК URL, но боевой поток через MulenPay Витрины не включайте до появления такого connector-а.

## Что работает сейчас

- Витрина: `POST /api/v1/external/payments` создаёт платёж через `PAYMENT_PROVIDER` Витрины; `GET /api/v1/external/payments/{transaction_id}` возвращает статус этого платежа.
- Merchant QR API панели сам выбирает случайного активного пользователя с непустым email из глобального списка пользователей панели; партнёр email не передаёт. Тот же `merchant_transaction_id` идемпотентно возвращает существующую операцию и не выбирает нового покупателя.
- Новый независимый `merchant_transaction_id` может выбрать тот же email повторно: в текущем пуле нет эксклюзивной резервации email на один открытый платёж.
- Для MulenPay поле `qr_url` у Витрины содержит hosted checkout URL. Это ссылка, которую можно закодировать в QR; это не прямая ссылка НСПК.
- Панель принимает отдельный merchant QR API `POST /api/v1/transactions/qr`, авторизованный токеном проекта. В его запросе есть сумма, валюта и `merchant_transaction_id`, но нет email. Этот endpoint сейчас требует прямую ссылку `https://qr.nspk.ru/...` и не принимает hosted URL Витрины как эквивалент НСПК QR.
- Импорт email панели как раз наполняет пул для этого merchant QR API.

Следовательно, авто-выбор email уже работает, но **не выдавайте партнёру ключ Витрины, ожидая, что платёж автоматически пойдёт через лимиты панели**. Для целевого потока потребуется connector между панелью и API Витрины и поддержка hosted URL как отдельного типа результата. Сейчас Merchant QR API панели требует результат провайдера с URL `https://qr.nspk.ru/...`; hosted URL Витрины на MulenPay не считается таким QR.

## Развёртывание панели на том же сервере

### 1. Витрина и общий Caddy

1. На сервере Витрины проверьте `.env`: `SITE_ADDRESS`, `PUBLIC_URL`, `ACME_EMAIL` и `PANEL_ADDRESS=panel.<домен-витрины>` должны содержать реальные значения.
2. Установите обновлённые `docker-compose.yml` и `Caddyfile` Витрины. Для локальной копии с изменениями используйте из репозитория Витрины `./scripts/deploy.sh root@<IP-сервера> /opt/vitrina`; скрипт синхронизирует файлы, не перезаписывает `.env` и перезапускает Compose.
3. Убедитесь, что стек Витрины запущен: `cd /opt/vitrina && docker compose ps`. Проверьте общую сеть: `docker network inspect vitrina_proxy`.
4. Caddy Витрины продолжает единолично принимать публичный трафик на 80/443 и выпускает TLS для `panel.<домен-витрины>`. Не запускайте для панели отдельный Nginx/Certbot и не публикуйте её внутренние порты в firewall.

### 2. Отдельная база панели и её секреты

Сначала доставьте код панели на сервер. Предпочтительный путь — включить нужные изменения deployment в коммит и отправить его в remote, затем на сервере клонировать private/public репозиторий с deploy key:

```bash
git clone <SSH-URL-РЕПОЗИТОРИЯ-PANEL_QR> /opt/panel-vitrina
cd /opt/panel-vitrina
```

Если `/opt/panel-vitrina` уже является клоном, не клонируйте поверх: выполните `git status --short`, сохраните локальные конфиги, затем `git pull --ff-only`. Не коммитьте `.env.production`, ключи, пароли или дампы. Для незакоммиченного локального кода используйте контролируемую передачу файлов, например `rsync` без удаления серверных секретов; не копируйте файл `.env.production` с компьютера.

В каталоге панели создайте production env:

```bash
cp .env.production.example .env.production
chmod 600 .env.production
sh scripts/generate-secrets.sh
```

Внесите выведенные значения в `.env.production`, затем задайте уникальную конфигурацию экземпляра:

```env
COMPOSE_PROJECT_NAME=panel-vitrina
DEPLOY_MODE=caddy-shared
PROXY_NETWORK=vitrina_proxy
PANEL_DOMAIN=panel.<домен-витрины>
POSTGRES_DB=panel_vitrina
POSTGRES_USER=panel_vitrina
API_BIND_PORT=18180
PANEL_BIND_PORT=15174
COMPOSE_PROFILES=processing
```

`POSTGRES_PASSWORD`, `ADMIN_TOKEN`, `OPERATOR_TOKEN`, `VIEWER_TOKEN` и `PANEL_SESSION_SECRET` должны быть случайными и уникальными. Скрипт `generate-secrets.sh` выводит эти значения и спрашивает у вас пароль администратора; сам пароль он не генерирует и не сохраняет, записывается только hash. Сохраните выбранный пароль в менеджере паролей. `ADMIN_TOKEN` — токен администрирования API панели, его не передавать партнёру.

Установщик `install-production.sh` при первом запуске ещё раз запросит пароль и перезапишет hash. Введите тот же пароль повторно (или не используйте hash из вывода генератора, если хотите задать пароль только на установщике). Секреты `POSTGRES_PASSWORD` и токены переносите в `.env.production`, не в командную историю и не в Git.

Первичная установка:

```bash
sudo bash scripts/install-production.sh
```

После установки выполните указанную скриптом команду в каталоге Витрины:

```bash
cd /opt/vitrina
docker compose up -d caddy
```

Проверьте `https://panel.<домен-витрины>`, `https://panel.<домен-витрины>/ready` и состояние сервисов:

```bash
cd /opt/panel-vitrina
docker compose --env-file .env.production -f docker-compose.prod.yml ps
docker compose --env-file .env.production -f docker-compose.prod.yml logs --tail=100 api worker
```

Панель использует отдельный volume PostgreSQL. Не задавайте одинаковые `COMPOSE_PROJECT_NAME` для разных установок и никогда не запускайте `docker compose down -v`.

### 3. Создайте проект панели и заведите провайдера

1. Откройте `https://panel.<домен-витрины>` и войдите в панель с именем `PANEL_ADMIN_USERNAME` и выбранным при установке паролем.
2. Создайте проект магазина. Запишите его `external_key`; выберите проект перед настройками подключений и лимитов.
3. Создайте подключение/маршрут для провайдера, который должен создавать фактический платёж. Задайте валюту, включённые методы, лимиты количества/суммы, лимит очереди и ограничения маршрута. Не включайте незнакомый провайдер и не подставляйте ключи MulenPay Витрины в произвольные поля панели.
4. Для автоматического выбора email откройте «Пользователи» → «Импорт email» и загрузите `.txt` или `.csv`, в котором адреса распознаются как email. Интерфейс нормализует регистр, убирает дубликаты в файле и отправляет записи пакетами. Уже существующие адреса пропускаются. Убедитесь, что импортированные записи активны и имеют email; только такие записи участвуют в выборе.
5. Выбор пула глобальный по панели, не ограничен выбранным проектом. На каждое новое значение `merchant_transaction_id` система случайно выбирает одного активного пользователя с email. Повтор с тем же merchant ID возвращает исходную транзакцию. Повторное использование email разными открытыми транзакциями возможно; email не резервируется эксклюзивно.
6. До тестового запроса убедитесь, что маршрут проекта ведёт к провайдеру, реально возвращающему прямой URL `https://qr.nspk.ru/...`. Если провайдер возвращает только hosted checkout URL, этот Merchant QR endpoint сейчас вернёт `502 sbp_qr_unavailable`; не используйте его для боевых платежей через hosted ссылку Витрины.

### 4. Выдайте партнёру правильные ключи и URL

Для текущего merchant QR API партнёру нужен **один входящий ключ проекта**: `external_incoming_token`. Сгенерируйте отдельный случайный токен на каждый merchant/project:

```bash
openssl rand -hex 32
```

В интерфейсе панели откройте «Настройки» выбранного проекта → «Внешняя площадка», сохраните этот секрет как входящий токен. Не путайте его с `ADMIN_TOKEN`/`OPERATOR_TOKEN`/`VIEWER_TOKEN` панели.

Передайте партнёру:

- URL создания: `https://panel.<домен-витрины>/api/v1/transactions/qr`.
- Метод: `POST`.
- Заголовок: `Authorization: Bearer <external_incoming_token>`.
- Валюту, формат суммы и диапазон, которые согласованы с проектом и провайдером.
- Требование генерировать стабильный уникальный `merchant_transaction_id` на заказ и повторять именно его при сетевой ошибке.

Запрос текущего API:

```http
POST https://panel.<домен-витрины>/api/v1/transactions/qr
Authorization: Bearer <external_incoming_token>
Content-Type: application/json
```

```json
{
  "amount": "500.00",
  "currency": "RUB",
  "merchant_transaction_id": "merchant-order-000123",
  "description": "Оплата заказа",
  "webhook_url": "https://merchant.example/payments/callback"
}
```

Ответ содержит `id`, `merchant_transaction_id`, `expires_at`, `amount`, `currency`, комиссию и `payment_url`. Текущий endpoint возвращает только прямой НСПК URL; отдельного поля для QR-картинки нет — партнёр может закодировать `payment_url` в QR, если его checkout это ожидает.

В примере `webhook_url` замените на реальный HTTPS callback партнёра. После терминального статуса текущая реализация отправляет JSON вида:

```json
{
  "merchant_transaction_id": "merchant-order-000123",
  "paid_amount": "500.00",
  "status": "paid",
  "type": "in"
}
```

Статусы также могут быть `failed`, `cancelled` или `refunded`. Этот callback от Merchant QR API не содержит подписи/секрета и не должен считаться криптографически аутентифицированным; приёмщик должен как минимум ограничить URL и использовать собственный защищённый механизм подтверждения. В панели есть trace транзакции и журнал попыток доставки.

### Важное про второй ключ и callback

В проекте есть также `external_callback_secret`. Это **не второй ключ авторизации для `/transactions/qr`**. Он используется другим endpoint `POST /api/v1/external/{project_key}/orders`: входящий `X-Platform-Token` авторизует площадку, а `external_callback_secret` подписывает финальный callback панели заголовками `X-Panel-Timestamp` и `X-Panel-Signature`.

Эндпоинты не взаимозаменяемы:

- `/api/v1/transactions/qr` выбирает email автоматически и принимает merchant token, но callback на `webhook_url` в текущем коде **не подписан**. Второй `external_callback_secret` к этому webhook не применяется. Получатель не должен считать неподписанное уведомление доказательством оплаты без дополнительной проверки.
- `/api/v1/external/{project_key}/orders` поддерживает подписанный callback, но требует `user_id` и `product_sku`; он не выбирает случайный email из пула.

Если партнёру обязательно нужны два секрета именно для входящего API и проверки исходящих статусов, это поведение сначала нужно реализовать/согласовать. Не выдавайте `external_callback_secret` как будто он уже подписывает merchant QR webhook. Для текущего QR API безопаснее потребовать от партнёра проверять статус по согласованному доверенному механизму; публичного merchant status GET с тем же project token сейчас нет.

## Ключ API Витрины для connector-а: пока не передавать партнёру

Для будущего connector-а «панель → API Витрины» понадобится отдельный токен Витрины. Сгенерируйте его только когда connector реализован и протестирован:

```bash
openssl rand -hex 32
```

Добавьте его в `PAYMENTS_API_TOKENS` в `/opt/vitrina/.env` в JSON-массиве. Этот ключ должен храниться на стороне панели как provider credential и не выдаваться traffic-партнёру:

```env
PAYMENTS_API_TOKENS=["<случайный-токен>"]
```

Пересоздайте API и worker Витрины, чтобы они получили настройку:

```bash
cd /opt/vitrina
docker compose up -d --force-recreate api worker
```

Партнёру этот токен не передавайте: его API-клиентом должна быть панель. На каждого connector/инстанс используйте отдельный токен; не передавайте `ADMIN_TOKEN`, `OPERATOR_TOKEN`, `VIEWER_TOKEN`, пароль админки, ключи MulenPay/PayHot или `.env`.

Создание платежа:

```http
POST https://<домен-витрины>/api/v1/external/payments
Authorization: Bearer <выданный-токен>
Content-Type: application/json
```

```json
{
  "transaction_id": "<новый UUID для заказа>",
  "email": "buyer@example.com",
  "amount_rub": 500
}
```

Вместо `email` допускается `user_id` Витрины; нужно передать ровно одно из этих полей. Сумма задаётся целым числом рублей, допустимый диапазон сейчас 100–500000. Партнёр должен создать UUID один раз и повторять запрос с тем же UUID при сетевых ошибках. Нельзя повторять заказ с тем же UUID, но другим email или суммой.

Ответ включает `transaction_id`, `status`, `paid`, `payment_url` и `qr_url`. Для MulenPay `payment_url`/`qr_url` — hosted платёжная ссылка, которую можно показать кнопкой или закодировать в QR. Партнёр проверяет результат:

```http
GET https://<домен-витрины>/api/v1/external/payments/<тот-же-UUID>
Authorization: Bearer <выданный-токен>
```

Возможные статусы Витрины: `pending`, `succeeded`, `failed`, `canceled`; успех подтверждается `paid: true`. Статус обновляет worker Витрины примерно раз в 30 секунд; проверка API читает сохранённое состояние, это не мгновенный синхронный запрос к провайдеру.

**Этот API-токен сейчас не подключает платежи к панели и её лимитам.** Вызов приведённых ниже методов создаёт самостоятельный платёж Витрины; панель его не видит. Примеры оставлены для проверки API и будущего connector-а, а не как готовый merchant-контракт через QR-панель.

## Загрузка email и принцип авто-выбора

Загрузите адреса в панель, поскольку пул для merchant QR выбирает именно панель:

- Войдите под администратором, откройте «Пользователи» → «Импорт email» и загрузите `.txt` или `.csv` с адресами. Клиент извлекает email из файла, нормализует их в нижний регистр и загружает пакетами. Сервер убирает дубли и пропускает адреса, уже имеющиеся в панели; интерфейс покажет количество добавленных/пропущенных.
- Проверьте, что импортированные пользователи активны и у них сохранён непустой email. Выбор не связан с `project_id`: пул пользователей глобален для панели.
- При каждом новом `merchant_transaction_id` endpoint выбирает одного случайного активного пользователя с email. Выбранный `user_id` и email попадают в запрос к провайдерскому адаптеру панели, не возвращаясь партнёру в открытом виде.
- Сетевой повтор с тем же `merchant_transaction_id` возвращает прежнюю транзакцию и не должен выбирать другой email. Отправляйте уникальный merchant ID на каждый заказ.
- Отдельные новые заказы могут повторно выбрать тот же email. Если нужна гарантия «один email — один незавершённый платёж», понадобится доработка с reservation/lease и освобождением по оплаченному, отменённому или истёкшему статусу.
- Витрина принимает email/user_id, переданный в запросе, и при неизвестном email создаёт аккаунт Витрины. Она не резервирует случайный адрес из базы панели.

Не загружайте один и тот же пул в обе базы в предположении, что системы синхронизируют его: такой синхронизации сейчас нет. Панель может выбрать email, но для передачи именно выбранного адреса в API Витрины нужен connector. Кроме того, если требуется никогда не использовать один email для двух одновременно открытых платежей, надо добавить резервирование и освобождение адреса по финальному статусу/expiry; текущая случайная выборка этого не гарантирует.

## Что добавить, чтобы ссылка приходила автоматически через панель

До включения целевого партнерского трафика нужен следующий поток:

1. Партнёр вызывает защищённый merchant endpoint панели с идемпотентным ID операции, суммой и необходимыми данными заказа.
2. Панель выбирает email из пула и вызывает connector Витрины: `POST /api/v1/external/payments` с сохранённым UUID операции, выбранным email и суммой. Если нужен запрет повторного использования email пока платёж открыт, connector должен атомарно резервировать его и снимать резерв по финальному статусу/expiry.
3. Connector получает `payment_url`/`qr_url` из ответа. Hosted URL кодируется в QR как hosted-ссылка; прямой `nspk_url` принимается и маркируется отдельно. Не объявлять hosted URL ссылкой НСПК.
4. Панель возвращает партнёру ссылку/QR в заранее согласованном контракте и проверяет статус через API Витрины либо получает подписанный callback. Лимиты, очередь и rate limits панели применяются до обращения к Витрине.
5. Повторы создания с тем же UUID не резервируют другой email и не создают второй платёж; если Витрина временно недоступна, операция остаётся повторяемой и аудируется.

Эти этапы требуют отдельной реализации и тестирования. До их завершения нельзя обещать партнёру выбор email из пула, маршрутизацию через лимиты панели или автоматическую прокладку hosted URL Витрины через панель.

## Проверка перед боевым трафиком

- Создать отдельный тестовый токен и тестовую операцию на минимально допустимую сумму.
- Убедиться, что повтор запроса с тем же UUID возвращает ту же операцию, а смена суммы/email с прежним UUID отклоняется.
- Проверить, что партнёр не получает административные ключи и не может видеть пользователей, настройки провайдеров или токены.
- Для целевого потока через панель дополнительно проверить выбор/резерв email, лимитирование, timeout/retry, формат QR (hosted или НСПК), получение финального статуса и отсутствие двойного платежа.
- После проверки отозвать тестовый токен и выпустить отдельный production token для партнёра.
