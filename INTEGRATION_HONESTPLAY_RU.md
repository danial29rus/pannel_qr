# HonestPlay → подключение к резервной панели

Панель `https://panel-trader.workkit-studio.ru` обращается к работающему HonestPlay как партнёр. HonestPlay сам создаёт платежи в MulenPay и проверяет их. Менять ключи MulenPay или webhook действующего проекта не требуется.

Реализация следует переданному документу: `POST /api/public/payments`, `GET /api/public/payments/{uuid}`, авторизация `X-API-Key`, RUB, UUIDv4, сумма с точностью до копейки, email покупателя и необязательное описание до 255 символов.

## Подключение в панели

1. Создайте проект в разделе «Проекты» и пользователей с реальными email покупателей, полученными вашим сервисом для оплаты.
2. Откройте «Подключения» (на телефоне — «Ещё» → «Подключения»).
3. Выберите **HonestPlay · партнёрский API**, задайте имя и уникальный системный код, например `honestplay-reserve`.
4. Адрес из документа: `https://2.27.42.108`. Укажите выданный владельцем HonestPlay `X-API-Key` только в закрытом поле формы. Сохраните подключение, выберите нужный проект и нажмите «В проект».
5. Настройте лимиты маршрута. Комиссия провайдера и ставка площадки — ваши договорные значения, документ их не определяет.
6. Включите `COMPOSE_PROFILES=processing` на новом сервере и выполните команду обновления из `DEPLOYMENT_RU.md`, чтобы worker опрашивал статусы. Интервал проекта задаётся в настройках; разумный старт по документу — 20 секунд.

TLS проверяется стандартно. Если сертификат HonestPlay не подходит для IP `2.27.42.108`, нужен его корректный HTTPS-домен или доверенная настройка сертификата; отключать проверку TLS в коде не следует. Без действительного ключа и доступного HTTPS реальная связность не проверена.

## Создание платежа через внутренний API панели

Backend, управляющий панелью, может использовать `POST /api/v1/transactions` с ролью operator/admin. Не выдавайте общий токен панели сторонним покупателям или браузеру. Для стороннего мерчанта потребуется отдельно согласовать его входящий контракт и доступ только к своему проекту.

Сгенерируйте UUIDv4 **до первого запроса** и сохраните рядом с заказом. Для повтора сохраняйте UUID, сумму и пользователя:

```http
POST https://panel-trader.workkit-studio.ru/api/v1/transactions
X-Panel-Token: <токен backend оператора>
Idempotency-Key: <сохранённый UUIDv4>
Content-Type: application/json
```

```json
{
  "project_id": "UUID проекта панели",
  "user_id": "UUID покупателя с email",
  "provider_code": "honestplay-reserve",
  "direction": "incoming",
  "amount": "100.50",
  "currency": "RUB",
  "description": "Оплата заказа"
}
```

`provider_code` можно опустить, если баланcировщик проекта должен выбрать подключение. В случае нескольких систем проверьте правила маршрутов. Пустые суммы, дробные копейки, другая валюта, выплаты и некорректный UUID отклоняются до запроса к HonestPlay.

Панель передаёт сохранённый UUID в HonestPlay и использует его как `external_id`. Повтор после сетевого сбоя или отката локальной записи не создаёт новый UUID. Если ваш внутренний Idempotency-Key не UUID, передайте сохранённый UUIDv4 в `extra.payment_uuid`; не генерируйте его заново при повторе. В пределах одного HonestPlay-аккаунта UUID должен быть уникальным для заказа, в том числе между проектами панели.

Повтор с тем же ключом и другой суммой, валютой, пользователем или направлением возвращает `409`. Изменение email пользователя между повторами не меняет email уже созданного заказа; HonestPlay также проверяет соответствие UUID, суммы и email. Не редактируйте покупателя во время создания/повтора его платежа.

В ответе панели `id` — локальный ID, `external_id` — UUID HonestPlay, `payment_url` — ссылка на оплату. Статусы и история видны в «Платежах»; worker получает их из HonestPlay. Исходный API-ключ и email не включаются в payload ответа адаптера.

## QR и статусы

HonestPlay возвращает **ссылку на платёжную страницу** MulenPay. Её можно показать как кнопку или закодировать в QR. Получение прямой ссылки `https://qr.nspk.ru/...` в данном документе не описано. Поэтому текущий `/api/v1/transactions/qr`, чей контракт требует прямой QR НСПК, отклоняет этот адаптер до создания удалённого платежа. Для него используйте подключения, действительно возвращающие НСПК, либо согласуйте отдельный входящий checkout-контракт для hosted-ссылок.

Панель считает платёж успешным только при одновременном `status=paid` и `payment_status=paid` в ответе HonestPlay. `provider_status=3` отдельно недостаточно. Неизвестные или противоречивые состояния остаются ожидающими. `cancelled + failed` становится ошибкой, `cancelled + cancelled` — отменой. Сумма GET переводится из копеек в рубли и сверяется с локальной суммой.

Webhook от HonestPlay не используется и не принимается: по документу предусмотрен опрос. Не направляйте старые MulenPay webhook на резервную панель.

## Что нужно для реального запуска

Нужны доступ к **новому** серверу, настроенный DNS/TLS панели, рабочий HTTPS-адрес HonestPlay, выданный партнёрский ключ и согласованный покупатель/сумма для первого реального платежа. Сначала проверьте доступность и чтение статуса существующего тестового UUID; затем выполните один согласованный тест создания. Автотесты адаптера используют подменённый HTTP и не создают реальные платежи.

В примере curl исходного документа после `email` стояла лишняя запятая — такой JSON сервер отклонит. В примерах выше JSON корректный.
